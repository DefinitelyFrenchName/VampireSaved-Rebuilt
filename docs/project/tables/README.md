# tables — the rebuild's documented tables (rule 5, `CLAUDE.md` [VSR-6])

**What this document is.** The specification of record for the tables in this directory: what each holds, its format
and why, where its values come from, and the gate that holds them. Phase 0 (`SPEC.md` §3) fills them from the
original (`DefinitelyFrenchName/VampireSaved`), read only, at `bf92acd2` (`SPEC.md` §0). Gameplay values come first,
by the maintainer's ruling.

in-table (the `edges_in` rows, in its `select_wheel.md`) and 221 baked.

## The format, and why

**One TSV per subject, one schema for all**: `manifest, kind, row, key, value, line, prov_kind, prov_refs`. Each line
is one value.
- `manifest` and `kind` are the original's file and table kind. `row` is the row's `name`, or `#n` (its ordinal within
  its kind in that file) for the three rows that have none; for JSON it is the value's concrete path. `key` is the
  field.
- `value` is the manifest's literal, as written (`true`, `0x0F`, `"donovan"`), so a renderer can reproduce the
  manifest exactly.
- `line` is the value's line in the original at the pin (`-` for JSON, which has no comments and no lines that carry
  provenance).
- `prov_kind` and `prov_refs` are what the original's census attributes to the value: the first of its provenance
  words (`measured`, `ruled`, `derived`, `testimony`, `maintainer`; `none` when absent or when the block is a
  retraction), and the session keys, tickets and dates the block names. The full paragraph is at `line` in the pinned
  original.

**Why this format** (`SPEC.md` §4, "the manifest subset", decided afresh):
- **TSV**, because the community reviews these values and a reviewer reads, greps and diffs a TSV without a parser.
  The original's registries are TSV for the same reason.
- **One schema**, because the census, the renderer and the gate then read every table the same way.
- **Literal values**, because phase 0's proof is that the original's manifests are reproduced from the tables.
- **References, not paragraphs**, because the comment blocks run to whole paragraphs, can quote bytes, and stay
  readable at their pinned line. Whether the rebuild carries them verbatim is decided when phase 1 needs them.

The rows are keyed by subject rather than by manifest, because a reviewer asks "which rows only apply to the variant
slot", not "what is in donovan.toml".

**What these tables do not hold:** ROM bytes ([VSR-8]). The gameplay column is flags, ids, slot numbers and row names.
The `fact` column (8,520 values, among them hex fields) is phase 0's next step, and how its hex is carried is decided
then.

## Where the values come from, and the gate

GENERATED by `tools/extract_gameplay_tables.py <export> <pin> <out>`. The export is made by `tools/export_original.py`.
The extractor imports the original census (`tools/audit_rule5.py` in the export) and aligns each record with its row
(`tools/phase0lib.py`). Each table's header names the pin and the SHA-1 of every manifest read. Until phase 0 closes,
the tables are not hand-edited: a change comes from the original or from a ruling, through the extractor.

The gate is `python3 tests/test_phase0_gameplay.py`. It has four checks:
- G1: the tables regenerate byte-for-byte from the export.
- G2: the export's manifests have the SHA-1s the headers name.
- G3: the census's gameplay column and the tables are the same multiset, with unique row ids.
- G4: every cell equals an independent parse (`tomli` / `json`) of its manifest, and a TOML row's line reads
  `key = value`.

Its three declared controls are perturbed copies: `perturbed-value`, `dropped-row` and `perturbed-manifest`. Each must
fail exactly its declared checks, and `--control <name>` runs the gate on the copy, where it must FAIL.

Measured at creation (R-001): 236 rows; G1–G4 pass (0 only-in-census, 0 only-in-tables, 0 wrong cells); the three
controls FIRED; the three control modes `VERDICT: FAIL`. Provenance across the 236: `measured` 188, `ruled` 9,
`maintainer` 3, `none` 36.
